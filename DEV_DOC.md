# Developer guide

## Environment setup

Run the complete project inside a dedicated Linux VM. Install Docker Engine and its Compose plugin using the [official Docker instructions](https://docs.docker.com/engine/install/debian/), plus GNU Make, curl, and OpenSSL. Ensure your user can run Docker commands.

```sh
docker version
docker compose version
make --version
openssl version
```

## Named-volume placement

Before creating volumes, configure `/etc/docker/daemon.json` with the following key, replacing `your_login`. Merge it with existing JSON settings:

```json
{
  "data-root": "/home/your_login/data"
}
```

On a new dedicated VM:

```sh
sudo mkdir -p /home/your_login/data
sudo systemctl restart docker
docker info --format '{{.DockerRootDir}}'
```

For an already used Docker daemon, this setting does not move existing data. Stop containers and Docker before migrating its storage with permissions/ownership preserved. For example, with `rsync` installed:

```sh
docker ps -q | xargs -r docker stop
sudo systemctl stop docker.service docker.socket
sudo mkdir -p /home/your_login/data
sudo rsync -aHAX --numeric-ids /var/lib/docker/ /home/your_login/data/
sudoedit /etc/docker/daemon.json
sudo systemctl start docker
```

Retain the original storage until migration is verified. Docker's containerd image snapshots may live elsewhere; named volumes must be inside the required directory. Do not replace these named volumes with bind mounts or bind-backed driver options.

## Configuration and secrets

Copy `srcs/.env.example` to `srcs/.env` and set:

| Variable | Purpose |
|---|---|
| `DOMAIN_NAME` | Your `<login>.42.fr` domain |
| `DB_NAME`, `DB_USER` | Application database and SQL account |
| `WP_TITLE` | Initial site title |
| `WP_ADMIN_USER`, `WP_ADMIN_EMAIL` | Administrator identity; no `admin` substring in its username |
| `WP_USER`, `WP_USER_EMAIL` | Distinct subscriber identity |

Generate missing password files using the README commands. Keep the files under `srcs/secrets/`, mode `600`, with the directory mode `700`. Each password is generated by `openssl rand -hex 32`; the initializer validates that format before composing SQL. `.env` contains configuration, not passwords. Existing secret files must be preserved when rebuilding an installed site.

Compose resolves secret paths relative to `srcs/docker-compose.yml`. Passwords are mounted as secrets, not baked into images. WordPress makes a worker-readable runtime copy of its SQL secret, mode `400` owned by `www-data`. Its authentication salts are generated once in the website volume.

Add `<VM-IP> <domain>` to the hosts file on the browsing machine. When browsing inside the Docker VM, use `127.0.0.1`. The hosts entry contains no protocol or URL path.

## Build and launch

```sh
make config
make up
make status
```

The Makefile builds all custom service images through Compose and waits for readiness. For direct access:

```sh
docker compose --env-file srcs/.env -f srcs/docker-compose.yml build
docker compose --env-file srcs/.env -f srcs/docker-compose.yml up -d --wait
```

Each service uses its own Dockerfile and a local image named `<service>:inception`. Only the permitted Debian base is pulled; no prebuilt NGINX, WordPress, or MariaDB service image is used. Build downloads need outbound network access. WordPress and WP-CLI versions are pinned, with CLI SHA-256 and WordPress core checksum verification. Coordinate upgrades with the existing persistent application and database rather than treating an image rebuild as an automatic core upgrade.

## Source layout and startup

- `srcs/docker-compose.yml`: services, network, volumes, secrets, and readiness ordering.
- `srcs/requirements/<service>/Dockerfile`: custom service builds.
- `srcs/requirements/*/conf/`: NGINX, PHP-FPM, and WordPress configuration.
- `srcs/requirements/*/tools/`: entrypoints and configuration validation.

MariaDB initializes an empty database volume, provisions the application account through a temporary socket-only server, then executes its foreground daemon as PID 1. The provisioning marker is `/var/lib/mysql/.inception-ready`. Existing SQL passwords are not reset automatically.

WordPress installs files when absent, retains its existing data and salts, waits for an authenticated SQL connection, installs the site when needed, and creates a missing subscriber. WP-CLI runs as `www-data`; quiet mode prevents prompted passwords from being echoed in logs. PHP-FPM then runs in the foreground as PID 1. Its internal ping supports readiness ordering and is not a public website endpoint.

NGINX generates a local TLS certificate, expands only the domain placeholder, checks its configuration, and runs in the foreground. Docker DNS is refreshed to reach replaced application containers. It serves only HTTPS, mounts website files read-only, and blocks hidden files, direct configuration access, and PHP execution beneath uploads.

## Manage containers and storage

```sh
make logs
make stop
make up
make down
```

Inspect individual resources:

```sh
docker compose --env-file srcs/.env -f srcs/docker-compose.yml logs wordpress
docker compose --env-file srcs/.env -f srcs/docker-compose.yml exec mariadb mariadb -u root
docker network inspect inception_inception
docker volume inspect inception_database inception_website
```

The SQL console uses root's local Unix-socket authentication. Example queries are `SHOW DATABASES;`, `USE inception;` (substitute your configured name), and `SHOW TABLES;`. WordPress accounts are application records, not separate SQL accounts.

| Named volume | Container path | Host storage |
|---|---|---|
| `inception_database` | `/var/lib/mysql` | `/home/<login>/data/volumes/inception_database/_data` |
| `inception_website` | `/var/www/html` | `/home/<login>/data/volumes/inception_website/_data` |

These are ordinary local named volumes with no bind-backed options. They survive container deletion/recreation. `make down` preserves them; `down -v` and volume deletion destroy stored data. Keep a private consistent backup before modifying database storage.

## Credential maintenance

WordPress passwords can be changed through the dashboard. Record updated passwords privately; startup does not reset existing accounts from the secret files. The SQL connection password requires a coordinated change: stop WordPress, generate a private replacement, explicitly update the configured SQL user through the root socket, update `db_password.txt` to match, and recreate the database/application containers to refresh file-backed secret mounts. Disable SQL client history for that maintenance session with `MYSQL_HISTFILE=/dev/null`, and never put a password in shell arguments or Git.

## Verification

Check all services are healthy, only NGINX publishes port 443, and both volume mountpoints are beneath `/home/<login>/data`. Verify administrator/subscriber login and privileges, a published post, an uploaded image, and persistence after `make down`/`make up`. Use curl or OpenSSL to confirm TLS 1.2/1.3 connections and rejection of TLS 1.0/1.1. A local certificate warning is expected for self-signed TLS; verify the hostname before trusting it. Inspect the staged Git diff to ensure `.env` and secret files are absent.
